# AI-Assisted Engineering Verification Protocol

## Purpose

This protocol defines how AI may accelerate implementation without becoming the source of unverified engineering or research claims. The repository treats AI output as a proposal that must pass human understanding, deterministic tests, and evidence-backed review.

## Core rule

> AI may propose. Evidence decides. Humans remain accountable for claims and risky actions.

This rule applies to code generation, refactoring, test generation, documentation, experiment design, interpretation, and remediation suggestions.

## Verification gates

Every material AI-assisted change should pass the following gates before it is treated as repository evidence.

1. **Problem gate** — state the failure mode or research question independently of the generated solution.
2. **Understanding gate** — the contributor can explain the control flow, assumptions, failure semantics, and relevant trade-offs without relying on generated prose.
3. **Test gate** — deterministic tests cover expected behavior and important negative cases.
4. **Adversarial gate** — test malformed, missing, contradictory, duplicated, delayed, or stale evidence where applicable.
5. **Safety gate** — generated code must not weaken dry-run defaults, typed confirmation, policy boundaries, auditability, or human authorization.
6. **Measurement gate** — performance or quality claims require a versioned experiment and machine-readable result artifact.
7. **Reproduction gate** — another reviewer can execute the documented procedure from a clean environment or understand precisely why a platform-specific step cannot be reproduced there.
8. **Claim gate** — documentation states only what the evidence establishes and preserves explicit limitations.

## AI contribution labels

For substantial research-facing artifacts, record one of these roles:

- `AI_NONE` — no material AI assistance.
- `AI_EDITOR` — wording, formatting, or mechanical cleanup only.
- `AI_COPILOT` — implementation or test suggestions reviewed and understood by the contributor.
- `AI_EXPERIMENT_ASSIST` — assistance with experiment scaffolding or analysis; measurements remain generated by executable code.

These labels describe workflow provenance, not quality.

## What AI output cannot establish

Generated code or prose alone cannot establish:

- correctness;
- production readiness;
- novelty;
- statistical significance;
- causal superiority over a baseline;
- enterprise-scale reliability;
- safe autonomous remediation;
- authorship-level understanding.

## Reviewer defense checklist

A contributor presenting an AI-assisted component should be able to answer:

- What problem does this component solve?
- What invariant must never be violated?
- What alternative design did you reject and why?
- What happens when its dependency fails?
- Which test would fail if the implementation were subtly wrong?
- Which result is measured rather than asserted?
- What evidence would cause you to reject your current hypothesis?

## Research integrity

AI may help generate hypotheses or experimental scaffolding, but it must not fabricate observations, labels, citations, benchmark outputs, statistical results, user studies, production incidents, or external validation. Unknown results remain `TBD` until produced by a reproducible experiment.

## Engineering integrity

AI-assisted changes must preserve the repository's separation between observation, proof, policy permission, human authorization, execution, audit, and replay. An AI explanation is never an execution authorization.
